# Where each `__sinit` belongs

Measured 2026-10-07 against the source tree, then the high and medium
paths were rechecked on `c49a7f8436`. This note does not move a sinit.
`tools/sinit_owners.py` is the repo's own advisory report and was not
the source of these rows.

303 translation units define a `void __sinit_*(...) {` body. One file,
one definition. A declaration such as the one in `src/func_02071844.c`
is not a definition.

The destination is the C++ file that should own the globals this sinit
constructs. The function stays in the overlay `.init` cluster either
way. mwcc emits it. `tools/rombuild.py` renames that object's `.text`
section header to `.init` only while the object has exactly one `.text`.

## How a row was scored

For each sinit, take every `data_*` global it names whose address is in
the same module. A global read by exactly one other non-sinit file is a
vote for that file. A global read by nobody, or by several files, does
not vote.

- **High.** One folded file is the only reader of 3 or more of those
  globals, or that file names this sinit and is the only reader.
  108 rows. Nine of them are the second kind and rest on a single
  global plus the file's own comment.
- **Medium.** The only reader of 1 or 2 globals. 115 rows. 48 of those
  rest on one global.
- **Not one file.** The votes split. 5 rows.
- **No reader.** No other file names the globals. 75 rows. Seventeen
  are main, `__sinit_02074d90` through `__sinit_02075154`. Six bodies
  are empty: `__sinit_02074dbc`, `__sinit_02074dc0`, `__sinit_02074e80`,
  `__sinit_020750b4`, `__sinit_02075150`, `__sinit_ov006_02130a04`.

No folded file receives two high rows. Neighbor comments that only use
a sinit as an address bound were read and not counted as ownership.
`daObjCtMecha09_c` names `__sinit_ov065_0211c110` as the `.init` above
its `.text`; the seven globals belong to `daYurei_Mucho_c`.
`unit020b4aa4.cpp` names `__sinit_ov004_020b955c` as the previous unit.

## Why these are not folded into the cpp

Pasting the body into the class `.cpp` does not match, and the linker
cannot place it.

`notes/experiments/piano-2712-sinit-split.md` moved
`__sinit_ov063_0211e5fc` into `d_a_piano.cpp`. The C++ compile of that C
body differed by 19 words. The same struct copies compiled as C and as
C++ differ. 102 of the 108 high rows are `.c` files. The class files
are C++. The merged object also overflowed the licensed `.text` range
by the whole sinit, because a pasted function is another `.text`, not
a compiler `.init`.

The shape that does match is the one already used by
`src/game/actors/d_a_obj_fm_battan.cpp`: real global objects in the
class file, so mwcc emits `__sinit_<filename>` into `.init`, and
`symbols.txt` uses that spelling. `notes/sinit-ownership.md` says that
move is allowed only after the generated bytes, relocations,
registration order, and the linked module match. The daBrq probe in
`notes/sinit-dabrq-ownership.md` reproduced `__sinit_ov070_02122d80`
byte for byte, and all 34 relocations still spelled different symbols.
That is not a production fold. Doing it for all 108 would fail
validation.

`__sinit_ov023_02111aa8` is already that case. ov023 enrolls
`d_a_obj_fm_battan.cpp` for `.text`, `.init`, and `.ctor`, and the
symbol is `__sinit_d_a_obj_fm_battan.cpp`.
